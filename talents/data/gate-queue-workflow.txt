Combined design (phase 1 — what shipped)
- The queue STAYS the per-candidate work distributor. The
  candidate-mode consumer (verify → ingest, retries ×3 → DLQ,
  proven 500/500 in the slice) is UNTOUCHED — no change to its
  verify/ingest body, no change to search/trending/suggest, no
  change to refreshRecordStats (the concurrent stats-fix
  builder's area; their fix shipped in #63 and its tests are
  green in this suite).
- NEW: TalentDrainWorkflow (cf/src/drain-workflow.ts — thin
  WorkflowEntrypoint adapter; cf/src/drain-workflow-steps.ts —
  all step logic, no "cloudflare:workers" import so Node tests
  import it directly). It replaces the producer cron + flag +
  watchdog as the BACKLOG feeder:
  * pages candidates from D1 in verification-priority order
    (keyset cursor, encoded string — the same cursor the admin
    enqueue route uses), bounded pages (default 100, clamp 1–500);
  * enqueues batches onto talents-ingest via the existing
    enqueueCandidatePage (via "backfill-workflow");
  * sleeps between batches (default 10 min, clamp 1–60) — pacing
    + GitHub budget awareness reusing the hardening build's math
    exactly: stop above 500 inflight, halt while the rate budget
    is exhausted (sleep until the exhausted-until timestamp,
    capped 1h per sleep), page capped by (remaining − 500 reserve)
    / 8 worst-case calls, 30-min processing-lease cutoff so rows
    another transport is processing are skipped;
  * tracks batch completion via drain-health state (candidates,
    inflight, DLQ depth) and the live marker's progress fields;
  * handles DLQ arrivals: every drain-phase check sweeps
    recoverable DLQ entries first (the dlq-sweep path, limit 25),
    so a swept entry re-enters the queue and `done` stays false
    until it completes;
  * resumes from its durable checkpoint after any interruption:
    every branch reads a STEP RESULT (never a fresh D1 read
    outside a step), every step name comes from the loop counter
    only (never Date.now()), step results are small JSON summaries
    (≤1 MiB by construction);
  * single-instance guard: the admin start route refuses while a
    live instance exists (binding status is the truth; a stale
    marker is overwritten), and the instance's init step aborts
    itself with NonRetryableError if another live instance owns
    the marker.
- State (all D1 sync_state, no KV, no migration):
  drain:workflow:live   — JSON {id, startedAt, batchSize,
    sleepMinutes, maxBatches, cursor, enqueued, batches}:
    single-instance claim + progress checkpoint. Written by the
    start route (after create()), re-verified by the init step,
    cleared by the finish step (only when it still names this
    instance).
  drain:workflow:active — ISO start timestamp. The cron producer
    tick + daily trickle stand down while it is fresh (< 24h),
    so the Workflow is the ONLY feeder (single-producer
    invariant); stale after 24h so a crashed instance never
    blocks the tick forever.
  drain:workflow:last_run — JSON summary written by the finish
    step ({id, finishedAt, reason, batches, enqueued, checks}).
- Run loop (runDrainLoop): enqueue phase (batch → pace, until
  done / flag-off / no-queue / batch cap 300) then drain phase
  (check → wait, up to 144 checks ≈ 24h) until candidates==0
  AND inflight==0. Terminal reasons: done | flag-off |
  max-batches | check-limit | no-queue. Estimated steps for the
  current ~20k backlog: ~203 batches + ~4 drain checks ≈ 207
  counted steps (sleeps do NOT count) vs the 10,000 paid
  default — an instance covers the whole backlog with headroom.
- Admin routes (ADMIN_TOKEN-gated, 404 when the secret is
  unset, same pattern as the other admin routes):
  POST /admin/drain-workflow/start — flag-gated by
    QUEUE_DRAIN_ENABLED (409 when off), refuses while one is
    live (409, names the live id), 503 when the binding is
    missing. Body: optional {batchSize, sleepMinutes,
    maxBatches} (clamped). Creates ONE instance and writes the
    live marker + active flag.
  GET /admin/drain-workflow/status — {live, bindingMissing,
    lastRun, health} (health = drainHealth snapshot).
- Producer deconfliction (cf/src/discovery.ts, minimal edit):

Cutover start procedure (replaces the old flag-only cutover)
Preconditions (unchanged): stats fix deployed (#63 — done)
and a fresh verified ingest completes without DLQing
(cutover criteria from gate-queuedrain: sane rejection
reasons, ~0 DLQ arrivals, ≥~300/hr sustained).
1. Re-mint the admin token (cf/scripts/set_discovery_secrets.py).
2. POST /admin/drain-workflow/start (optionally with
   {batchSize, sleepMinutes, maxBatches}; defaults 100 / 10 /
   300). Expect 200 {id, status:"created", startedAt}. A 409
   means the flag is off (set QUEUE_DRAIN_ENABLED=1 first) or
   an instance is already live.
3. Watch: GET /admin/drain-workflow/status (live id + health)
   and GET /admin/drain-health (candidates falling, inflight
   ≤500, dlqDepth 0). First batch should enqueue ≤100 within
   ~10 min; the live marker's enqueued/batches advance in D1.
4. Once the Workflow is feeding (first batches confirmed in
   drain-health), stop the sandbox drain
   (scripts/backfill-drain.mjs) and remove the
   talents-backfill-drain-watchdog cron. Do NOT stop the
   sandbox drain before the Workflow's first batches land —
   the Workflow replaces the producer cron + flag + watchdog,
   and the cron tick now stands down while it is live.
5. If the Workflow errors or stalls: the flag is the kill
   switch — set QUEUE_DRAIN_ENABLED off and the loop finishes
   with reason "flag-off" at the next batch boundary (the
   finish step clears the marker; status shows lastRun). A
   duplicate start is refused while one is live; a crashed
   instance's marker goes stale (binding status complete /
   errored / terminated) and a fresh start overwrites it. The
   producer tick resumes automatically 24h after the active
   marker's timestamp if no instance is live.
6. Rollback: stop the Workflow instance (API terminate) or
   turn the flag off, then re-enable the producer tick path
   (it resumes once the active marker is stale/absent) or
   restart the sandbox drain. Nothing in this build deletes
   or reclassifies data — candidates stay candidates until
   the consumer ingests them.

Phase 2 — DESIGN ONLY (not built): per-candidate Workflow
Goal: fold today's separate enrich/embed sweeps into ingest,
so one durable per-candidate run does verify → ingest →
attest → enrich → embed, with per-step retries, instead of
five separate passes (queue consumer + enrich cron + embed
sweep + stats rebuild + DLQ sweep) that each re-read the
record.
- Trigger: the queue consumer (candidate-mode) starts ONE
  Workflow instance per verified candidate (or per ingest
  batch of N candidates — decision at build time; per-candidate
  keeps failure blast radius at one record, per-batch saves
  instance overhead; recommend per-candidate, measured against
  the 10,000-step paid default and the instance-creation rate
  limit).
- Steps (all durable, each with its own retry policy):
  1. verify — the existing verify path (fetch repo, parse
     SKILL.md/plugin.json, classify). Retry: transient GitHub
     errors only; deterministic failures → NonRetryableError
     + D1 rejection (same as today).
  2. ingest — the existing ingest/upsert + FTS indexing.
     Attest inside this step (registry key sign) so the record
     is never visible unattested.
  3. enrich — Layers A–D for THIS record only (assets,
     description repair, capabilities, editorial), reusing the
     existing layer functions; skip layers the record already
     has (idempotent, cheap re-run).
  4. embed — single-record embed into Vectorize (the embed
     sweep's per-record function, not the batched sweep).
  5. stats — incremental stats update for this record only
     (the stats-fix builder's incremental path, NOT the
     full-table refreshRecordStats).
- State: per-instance progress lives in the Workflow (step
  results); D1 stays the source of truth for record state
  (status, record_json, embedding_meta). No new tables
  expected; the instance id is recorded on the source row
  (new nullable column `workflow_instance_id`, migration) so
  an operator can find a record's run.
- DLQ: a step that exhausts retries errors the instance; the
  queue message's final attempt writes the DLQ manifest as
  today, and the DLQ sweep re-enqueues the message — which
  starts a FRESH instance (step results are not shared across
  instances; idempotent steps make the re-run safe).
- Migration plan (from phase 1 to phase 2):
  a. Build the per-candidate Workflow + its start call in the
     consumer behind a flag (e.g. WORKFLOW_INGEST_ENABLED),
     default off; keep the direct verify→ingest path as the
     fallback.
  b. Shadow-test on the sandbox drain's slice: run N
     candidates through the Workflow path, compare terminal
     states + record contents against the direct path
     record-by-record (zero diffs required).
  c. Flip the flag for new queue messages only; in-flight
     direct-path messages finish as-is (no migration of live
     messages).
  d. Retire the enrich/embed sweeps' cron triggers once the
     Workflow path has covered a full drain cycle with no
     DLQ growth; keep the sweeps as backfill tools for
     pre-Workflow records (they stay runnable, just
     untriggered).
  e. The phase-1 drain orchestrator (this build) is unchanged
     by phase 2 — it still pages candidates onto the queue;
     only the consumer's per-message handling changes.
  f. Cost watch: instance count = candidate count (~20k for
     the backlog, then steady-state discovery volume); confirm
     the Workflows plan's instance/steps pricing before
     flipping the flag for the backlog, and keep the batch
     option (d) as the fallback if per-candidate pricing is
     prohibitive.
- Open design questions for the phase-2 build (not decisions):
  per-candidate vs per-batch instances; whether enrich Layer D
  (Anthropic, ~$9.78/1k generated) runs inline per record or
  stays a batched sweep for cost; step retry counts per layer.
