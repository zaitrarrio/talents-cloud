GUARD DEFECT FOUND + FIXED DURING THE WATCH (not in the plan)
- Symptom (~03:35Z): GET /admin/drain-workflow/status reported
  live:null while the instance was verifiably running (Cloudflare
  API: status "running"), even though the D1 live marker existed
  (drain:workflow:live = the instance id, batchSize 100, cursor
  present) and the active marker was set.
- Root cause: cf/src/drain-workflow-steps.ts getLiveDrainWorkflow
  called `env.DRAIN_WORKFLOW.get(marker.id)` WITHOUT await. The
  real binding's get() is async (docs: get(id):
  Promise<WorkflowInstance>), so `inst` was a Promise,
  `inst.status()` threw TypeError, the catch returned stale.
  Consequence: live detection always reported stale — status
  showed live:null AND the single-instance guard in
  startDrainWorkflow (same function) was blind: a second POST
  start would have created a duplicate instance, and the duplicate's
  init step (same function) would not have aborted it. The
  "single-instance guarded" claim in gate-queue-workflow was not
  true live. The cron-tick stand-down was NOT affected (it reads
  the drain:workflow:active marker timestamp, not the binding).
- Why tests missed it: test/drainworkflow.test.ts fakeBinding had
  a SYNCHRONOUS get() returning the instance directly; the real
  binding returns a Promise. The fake was unfaithful.
- Fix (2026-11-12 ~03:36–03:39Z): one await —
  `const inst = await env.DRAIN_WORKFLOW.get(marker.id)` — plus
  WorkflowBindingLike.get() typed as Promise<WorkflowInstanceLike>
  in cf/src/db.ts, the test fake made async, and comments at all
  three sites. The two existing guard tests (start refuses while
  live; status reports live when running) now exercise the async
  fake and would fail on the old code — they are the regression
  coverage. Full suite: 325 tests, 324 pass, 0 fail, 1 skipped
  (pre-existing env-gated skip).
- Redeploy via cf/scripts/deploy_queueworkflow.py → Worker version
