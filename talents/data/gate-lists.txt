Design (ARCHITECTURE-v2 §7, src/discovery/lists.ts)
---------------------------------------------------
A curated list repo (awesome-* style) is its own source kind
("list", status "mined"): it is MINED for outbound links, never
listed, never ingested (ingestSource throws on kind "list"), and
never merely rejected when it is link-dense. Classification:
(a) explicit nomination — operator CLI `talents discover lists
--mine <owner/repo>`, or a scout flagging an awesome-*/best-of-*
name (web scout) — always a CLAIM, resolved by the tree check;
(b) the verification-time heuristic, wired into every rejection
path (scout runner, sweep cycle, backfill drain): tree has NO
skill files + markdown links to ≥10 distinct GitHub repos → list.
Records win unconditionally: a repo with records, or a tree with
skill files (checked at classification AND at every refresh), is
never a list. Mining nominates each link into the one funnel with
provenance {via:"list", list, section} — the section is the
nearest preceding markdown heading, stored as a category HINT on
the candidate, never auto-applied. Each list is its own
corroboration channel (store.provenanceChannelKey): two lists
naming the same repo corroborate it; the same list twice does not.
Caps: 500 nominations per list per run; markdown bounded to
root *.md + docs/**.md, 16 files, 256 KB each. Refresh: weekly —
Worker discovery cron re-mines known lists on Mondays (limit 8),
a push webhook to a known list re-mines it via the ingest queue,
and re-mining is idempotent with removals IGNORED entirely (a
dropped link's candidate is never unlisted or demoted — unit
tested). Graduated lists (repo grew skill files) return to the
normal funnel as verified sources.
