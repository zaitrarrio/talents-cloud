THE RULE (from gate-drainfix.txt, measured live)
-----------------------------------------------
D1 rejects any single SQL statement over 100,000 bytes
(SQLITE_TOOBIG, code 7500): a 90 KB statement succeeds, a 99 KB one
fails. All sizing here treats bound parameters as inlined (the
conservative reading, and exactly what the operator transport
does), so a statement that fits fits on both transports.

SHARED LAYER (paths cannot drift)
-----------------------------------------------
New module src/d1-limits.ts — no transport dependencies, imported
by the CLI, the tests, and the Worker bundle alike:
  MAX_D1_STATEMENT_BYTES = 90,000 (cap for any one statement)
  STATEMENT_BUDGET_BYTES = 80,000 (split-path trigger)
  TEXT_CHUNK_BYTES       = 40,000 (largest chunk per statement)
  chunkTextByBytes()     (moved from discovery/store.ts; identical
                          code-point-safe implementation)
  estimateStatementBytes(sql, params) — SQL bytes + bound values
                          sized as inlined (strings at UTF-8 length
                          + 2 quotes + 1 per single-quote for ''
                          escaping; numbers/null literal-sized)
  statementExceedsLimit()
src/discovery/wrangler-d1.ts now imports/re-exports
MAX_D1_STATEMENT_BYTES from d1-limits.ts (was a local const);
src/discovery/store.ts imports chunkTextByBytes from d1-limits.ts
and keeps RECORD_STATEMENT_BUDGET_BYTES / RECORD_TEXT_CHUNK_BYTES
as aliases of the shared values. No value changed anywhere.

TESTS
-----
Root suite: 222 tests, 221 pass, 0 fail, 1 pre-existing env-gated
skip (was 218 / 217 + 1 skip; +4 new, all passing).
test/d1harden.test.ts runs the real stores against real SQLite
(actual migration SQL) behind a strict D1Like that enforces the
production limit — any statement estimated >90,000 bytes throws
"statement too long: SQLITE_TOOBIG", so an unchunked regression
fails the way production would:
  (a) upsertRecord (the Worker ingest path) with a record whose
      record_json is ≥120 KB (120,000-char description + 400
      declaration lines): completes; every emitted statement
      ≤90,000 bytes; stored record_json byte-identical to
      JSON.stringify(record); search_text and FTS declaration_text
      complete.
  (b) D1EnrichmentStore.upsertLayer with a ≥120 KB layer-B-shaped
      payload (600 sub-inventory entries with CJK + emoji text —
      code-point safety): chunked path taken (≥2 || appends, every
      chunk param ≤ TEXT_CHUNK_BYTES), chunk sequence reassembles
      the payload byte-identically, store read-back JSON.stringify
      equals the original payload exactly; same round-trip for a
      ≥120 KB layer-D payload (no-*_at shape); small payload =
      exactly 1 statement; overwriting a chunked value with a
      small one leaves no appended residue.
  (c) appendSearchExtras over the ≥120 KB record: search_text and
      FTS description both take the chunked path; stored
      search_text equals the exact expected concatenation (bare
      text + derived extras + generated extras); FTS components
      contain the extras; declaration_text complete.
  (d) estimateStatementBytes: multibyte strings sized at UTF-8
      length (50,000 CJK chars ≈ 150,000 bytes → exceeds), single
      quotes counted double, numbers/null literal-sized.
  (The batched-write splitter for the operator transport —
  WranglerD1.flush — is covered by test/drainfix.test.ts; the
  Worker path has no batch() usage, its splitter is the chunk
  sequences asserted in (b)/(c).)

PRE-EXISTING DEFECT FOUND (not this change; flagged for the
parent agent)
----------------------------------------------------------------
The skill page for aaron-he-zhu/aaron-marketing returns 500:
"Something went wrong: c2.commands.map is not a function".
Grounded in production D1: in that record's stored record_json,
components.commands is a TEXT value, not an array
(json_type(record_json,'$.components.commands') = 'text', while
components.skills is 'array') — an ingest-shape defect in the
record data itself; the renderer maps over it and throws. This
change never writes record_json (enrichment touches only the
enrichment row, search_text, and skills_fts), the render code is
untouched, and the record's enrichment above succeeded — the page
defect is independent of the D1 hardening and predates it in the
record data. Other oversized records' pages verified healthy in
the same pass (apidojo-skills 200, xiaohongshu-complete-skills
200, all-ios-skills 200, k-skill 200). A tolerant renderer (or an
ingest-side components normalizer) would fix the class; out of
scope here.
