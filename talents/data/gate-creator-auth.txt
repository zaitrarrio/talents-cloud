== SEPARATE PRODUCTION INCIDENT (not caused by this swap) ==
Home / and /api/trending return 500; /api/search returns 200 with
vectorError "D1 query result exceeded the maximum response size limit
of 50 MB" and falls back to keyword-only. /search page itself is 200.
Mechanism: allRecords() (cf/src/db.ts) runs SELECT record_json FROM
records WHERE status='listed' — a full-table load. Production D1 now
holds 22,407 listed records totaling 50,865,333 bytes of record_json,
just over D1's 50 MB single-query response limit. trendingRecords()
calls allRecords() OUTSIDE its try/catch, so home and /api/trending
throw. The search vector block and the post-rank fallback hit the
same call. Home was 200 this morning at 16,096 records; the queue
slice + sandbox drain pushed the catalog past the threshold during
the day. My deploy touched auth + vars only and predates the
crossing in code terms — the failure is data-scale, not the swap.
FIXED IN THIS TASK (it blocked the dashboard verification):
catalogOwners issued 1 + owner-count sequential D1 calls per
dashboard/claim request (1,075 at 22,407 records) — past the Workers
1,000-subrequest-per-request ceiling, so /dashboard 500'd for every
signed-in user. Rewritten to a single (owner, source_repo) scan
(~1 MB), identical map, covered by a regression test.
NOT FIXED: allRecords callers — trendingRecords (home, /api/trending),
hybridSearch post-rank fallback, suggestForSkill. Fix shape: fetch
only needed records by id for trending (trending ids + a bounded
recent sample for the static fallback), bound the search fallback,
